# 定时任务的设计取向（同类调研 + 本次落地 + 待办）

日期：2026-09-23 ｜ 起源：用户反馈「定时任务设置界面让人不懂、太简陋」

## 一、同类调研：成熟 agent 产品怎么做（本地 DSH 仓库）

参考实现：`deepseek-harness` 的 `docs/user/guide/schedule.zh.md`、`docs/subsystems/schedule.zh.md`、
`.agents/notes/implemented/feature/2026-08-05-durable-web-schedule.zh.md`。

| 维度 | DSH 的做法 | 对我们的启示 |
| --- | --- | --- |
| 任务内容 | **提示词**（prompt），不是 shell 命令 | 用户想的是「让 agent 每天替我干活」，不是「跑条命令」 |
| 交付方式 | 到期后作为**一个普通对话轮次**投回原会话；**没有**独立回执卡片 | 避免第二套「交付」语义；结果天然可回溯 |
| 调度原语 | 只有三种：延时一次 / 绝对时刻 / 固定速率（最小 5 分钟） | 少量原语比 cron 更好懂 |
| 日历/Cron | **刻意不支持**（需时区敏感日历语言 + 求值器 + tzdata 回放策略，收益不匹配） | 我们也不该上 cron 表达式 |
| 时区 | 显式边界：自然语言时间必须由模型转成 RFC3339 或带 IANA 时区；DST 缺口拒绝、重叠取较早 | 「每天 9 点」必须说清是哪个时区的 9 点 |
| 逾期 | 只呈现**最新一次**到期时刻并直接推进到未来，**绝不积压回放**；多条逾期合并成一次 | 与我们「只补跑一次」一致（已在 Rust 侧实现并有单测） |
| 界面 | 只读目录（完整 prompt + 等待中/逾期 + 绝对与相对时间）；创建/编辑/删除交给模型工具 | 列表要回答「下次什么时候、上次成没成」 |
| 状态词 | scheduled / overdue，配相对时间（in 6 minutes / 5 minutes overdue） | 相对时间比时间戳好懂 |

## 二、本次落地（`657ed0f` 之后的定时任务改版）

**界面**（`src/components/ScheduledTasks.vue`）

- 两段式表单：**① 跑什么**（名称 + 命令，带 5 个可点示例）／**② 什么时候跑**（预设 chips + 自定义）
- 常用调度预设：每 15 分钟 / 30 分钟 / 1 小时 / 6 小时 / 每天 09:00 / 18:00 / 22:00（命中高亮）
- **下次运行实时预览**：`09-24 09:00（8 小时后）`
- 任务卡片：状态图标（成功 / 失败 / 超时 / 未运行）、调度摘要、下次时间 + 倒计时（逾期高亮）、
  上次运行时间、输出**折叠**展示（原来直接铺开 1000 字符）
- 操作：**立即运行**（验证配置，不改动下次时间）／启用暂停／**编辑**／删除
- 统一走 `notify` / `askConfirm`（WKWebView 下原生 alert/confirm 有已知问题）
- 所有按钮显式 `color` + 主题变量（修掉暗色主题下按钮黑字看不见的隐患）

**纯逻辑**（`src/utils/schedule-format.ts` + 9 条单测）：间隔人话化、相对时间、状态判定
（退出码优先，老数据回退文本启发式）、预设匹配与套用、下次运行计算（与 Rust `compute_next_run`
同语义：daily 已过/恰好等于→次日；interval ≤0→60 分钟）、表单校验。

**后端**

- `scheduled_tasks` 新增 `last_exit_code`（建表 + **幂等迁移** + 行映射 + 读写；2 条 db 测试，含旧库补列）
- 新命令 `run_scheduled_task_now`（立即运行一次，不动 `next_run_at`）
- 执行路径统一为 `exec_scheduled_command` → 复用 `run_shell_command_with`
  （并发读 stdout/stderr、**300 秒超时并杀掉整个进程组**、走 shell 语义）

  > 顺带修掉一个真实隐患：原调度器直接 `Command::new("/bin/sh")` 且**没有超时**，
  > 一条卡住的命令会把整条调度线程堵死（其它任务全部不再执行），而代码注释却写着「300 秒超时」。

## 三、待办（研究里值得吸收，本次未做）

按价值/成本排序：

1. **任务内容支持提示词**（`kind: command | prompt`）：让 agent 干活而不只是跑 shell。
   需要：DB 加 `kind`/`prompt` 列 + 调度线程分支（走 `chat_once`，参考 `im.rs` 里
   `LlmReplyGen` 读活跃 profile 的做法）+ 表单里切换「执行命令 / 让 Agent 执行」。
2. **结果对话式交付**：把到期任务的输出作为一条消息投回某个会话（而非只记在卡片里）。
   这是 DSH 最核心的一条设计；需要决定投递目标（专用会话 or 最近会话）与是否同时发系统通知。
3. **新增原语**：一次性（延时 N 分钟 / 指定日期时刻）。DSH 的 `after` 与 `at` 都很常用，
   我们目前只有 interval/daily。
4. **时区显式化**：目前 `daily_time` 是本地时间（隐含系统时区）。若要跨设备/跨时区，
   需存 IANA 时区并处理 DST 缺口与重叠。
5. **逾期并入通知**：任务长时间逾期（如应用关闭数天）时在启动后给一次汇总提示，
   而不是静默补跑一次。

## 四、明确不做

- **cron / 日历表达式**：与 DSH 同样判断——需要时区敏感的日历求值器与回放策略，
  而收益被「预设 + 间隔 + 每天时刻」覆盖大半。
- **独立回执卡片**：保持「结果只记在任务卡片」的现状，等对话式交付做好再统一。
