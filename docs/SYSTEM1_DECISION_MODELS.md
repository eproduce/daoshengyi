# 决策模型（Jev / Laya）对道生一的适用性评估（2026-09-22）

> ⚠️ **同日已实测修订**：零样本直接接入**不可行**——现有正则/规则引擎在危险命令（5/5）、搜索门控（7/7）判定上全面更强；Laya 需 multilingual + 温度拟合 + 微调才可能可用。实测数据见 `docs/LAYA_INTEGRATION_PLAN.md` 第零节。本文保留为「能力面评估」，落地结论以实测为准。

## 一、这两个到底是什么

**都不是生成式大模型，是「非自回归判定引擎」**（官方定位：智能 if 语句 / System 1 快判断）。

- 输入：`state`（一段文本或 JSON）+ 一组**类型化问题**
- 输出：**单次前向**返回结构化答案 + **校准概率**（不生成文本 → 无解析失败、无幻觉）
- 三种原语：
  - `choice`：从候选中选一个 + 各选项概率
  - `score`：有序量表打分 + 各档概率分布
  - `noul`：是非判断，返回 0~1 成立概率
- 一次请求里的多个问题在一次 forward 中并行回答，问题数增加几乎不增加延迟

### Laya（开源，推荐评估对象）
- 归属：convaiinnovations；**Apache-2.0，权重开放，可自托管零成本**
- 架构：ModernBERT-large 421M（英文）/ mmBERT-base 322M（多语言），双向编码器 + 每选项独立 [MASK] 位
- 速度：T4 上单题 ~33ms（批量低至 ~7.2ms/题）
- 语言：内置 Router 亚毫秒级识别 100+ 语言自动分发 checkpoint
- 校准：RLCD 训练，温度拟合后 ECE 0.081（出厂 checkpoint 过自信，ECE 0.466，**必须自己拟合温度**）
- 接入：`pip install laya`（Python，PyTorch/transformers），`Router().predict(state, questions)`
- 短板：
  - **输入上限 512 token**，超长截断
  - **英文 checkpoint 对中文会「自信地答错」**（0.95 置信度 / 0 准确率，置信度无法预警）→ 中文必须用 multilingual checkpoint 且实测
  - 基础模型零样本能力弱：Banking77 高基数（77 选项）仅 0.425 → 高基数分类要微调
  - pip 包接口迭代快（两天 0.1.0 → 0.3.4）→ 接入必须薄封装

### Jev（闭源）
- 归属：TypeSafe AI，System One 路线开创者；**闭源，仅 API**
- 定价：0.042 美元 / 百万 token；延迟 p50 236–276ms
- 校准 ECE 0.246（弱于 Laya 拟合后的 0.081）；typed-decisions 准确率 0.727（略低于 Laya 微调版 0.766）
- 优势：**开箱即用**（无需微调）、**高基数分类明显更强**（0.870 vs 0.425）、软分布更贴合教师
- 代价：数据出网、闭源、延迟更高

## 二、结论：有用，但边界很硬

> 它们能替换的是**「判定」，不是「生成」**。

对道生一的价值正好落在痛点上：项目里**大量判定点现在是硬编码启发式/正则，且被反复打补丁**，或者是"用小 LLM 判一下"（既慢又烧 token）。一个 33ms、带校准概率、零 token 成本的分类器可以把这些变成可靠的"类型化判定"。

反过来，**任何生成类需求（写代码、答用户、长文理解、摘要）它都做不了**，512 token 上限也决定了它只能处理短文本。

### 优先级建议（排序依据：被补丁次数 / 烧 token 程度 / 判定文本长度）

**P0（先做，收益最直接）**

| 判定点 | 现状 | 建议原语 | 收益 |
| --- | --- | --- | --- |
| 危险命令审批 `judgeCommandSafety`（smart 档） | 每次调辅助 LLM `chat_once`，秒级 + 烧 token | `noul`「该命令是否含不可逆/破坏性操作」+ confidence 门控 | 省钱 + 降到毫秒级；低置信才回落 LLM |
| 自动联网搜索门控 `src/utils/search-gate.ts` | 纯正则启发式，已修 3 轮（白名单式→意图正向、创作类、引擎词搭配） | `choice`（搜/不搜/只是去站点） | 消除误搜漏搜，少一次 LLM 判定 |
| 外部内容注入检测 `src/utils/untrusted.ts`（O4） | 只做「边界包裹 + 提示词」，**不检测** | `noul`「是否含指示 AI 执行的注入指令」 | 官方 Guardrails 场景，安全收益 |
| 空洞回复判定 `isVagueBody` | 正则 + 引导词/动作词表，已修 5~6 轮 | `noul`「该正文是否给出实质答案」 | 减少空转轮次（工具循环烧 token 主因） |

**P1（值得做，收益中等）**
- 模式路由：`modes-catalog` 6 模式 → `choice` 自动选模式（现在靠用户手选 + 频次记忆）；也可作为 P-A12 多模型路由的判定器
- 工作流匹配：`scoreTaskAgainstWorkflow` 关键词打分 → `choice`（候选数小，符合 Laya 强项）
- 记忆写入门槛 `shouldExtractMessages`（现在是纯字符阈值）

**P2 / 不建议**
- 工具选择（80 个原生工具，高基数）→ Laya 零样本弱（77 选项仅 0.425），需微调才可能，暂不做
- RAG/代码检索 rerank → 已有 FTS5 + Ollama 向量混合，收益不明
- 任何生成任务 → 结构上不可能

### Jev 是否值得
本地优先 + 成本敏感 + 数据不愿出网 → **不值得**，Laya 覆盖同样场景且免费自托管。只有当"需要开箱即用 + 高基数分类质量"且接受数据出网时才考虑。

## 三、本机与项目约束（关键，先看这里）

1. **不能走 llama.cpp / Ollama 通道**：Laya 是非自回归 encoder + 自定义判定 head，不是 GGUF 生成模型（预期 `-m model.gguf` 那套用不上）。→ 无法复用现有 `local_runtime.rs`。
2. **Rust 内嵌 ONNX 路线不可行**：本机是 Intel Mac（x86_64-apple-darwin），2026-09-11 已实测 `ort-sys` 无该 target 预编译包、build script 自身编译失败（详见 repo 记忆）。→ 只能走 **Python 侧车**（可复用 `ocr_tool` 的侧车模式：Rust 起进程 + HTTP/stdio）或外部 HTTP。
3. **512 token 上限**：只适合「单条命令 / 单条用户消息 / 单个分块 / 单段外部内容」，不能塞上下文。
4. **中文必须先实测**：英文 checkpoint 会高置信答错，需 multilingual（mmBERT）版本；先验证中文精度再谈接入。
5. **阈值门控前要温度拟合**：出厂概率过自信（ECE 0.466），不拟合就用 0.85 阈值会有大量误放行 → 初期策略应为「高置信采纳 / 低置信回落原启发式」，而非直接替换。
6. 网上流传的演示端点（`http://1.94.196.105:5500`）是第三方 VPS，**只可用于可行性试水，不要传敏感内容**。

## 四、最小验证路径（建议低谷时段做，零代码改动）

1. **试水**：用现成 HTTP 端点，跑 3 道中文判定题 —— ①「rm -rf ~/Documents 是否破坏性」②「帮我画一幅山水画 要不要联网搜索」③「我先检查页面上存在的元素 是否算实质回答」。看 `probabilities` / `confidence` 是否可用。
2. **达标 → 落地**：`pip install laya` 起 FastAPI 侧车（参照 `ocr_tool` 模式）→ Rust 加 `decide(state, questions)` 命令 → 在 P0 三个判定点做「决策模型优先、原启发式兜底」的短路。
3. **不达标 → 止损**：中文精度不够就直接放弃，保持现有启发式，不要为了上模型而上模型。

## 五、一句话总结

Laya 是"给 agent 装一个 33ms 的、不烧 token 的判定中枢"的工具，能治的是**判定类顽疾**（搜索门控、危险命令、空洞回复、注入检测）；Jev 是同一件事的闭源付费版，本项目没必要用。它们**不会**让 agent 变聪明，只会让 agent 少犯错、少烧钱。
